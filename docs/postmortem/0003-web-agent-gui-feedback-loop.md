# ポストモーテム 0003: Web エージェントが現在の GUI ではなく代替サーバーを検証した

日本語 | [English](0003-web-agent-gui-feedback-loop.en.md) | [中文](0003-web-agent-gui-feedback-loop.zh.md)

ステータス: 解決済み

## エグゼクティブサマリー

Web エージェントは GUI のソースを変更したが、自分のセッションをホストしている URL とプロセスを把握していなかった。受け入れ検証をユーザーに委任し、続いて `window.__DSH_BOOT__` が欠落した白画面にもかかわらず素の Vite HTTP 200 を成功とみなし、最終的には元のページが再ビルド済み成果物をすでに取り込んでいたのに、別ポートで代替の `dsh web` サーバーを検証した。修正により、現在の URL とランタイムモードがモデルから参照可能かつシェルから照会可能になり、listen 前のスタンドアロン Vite が拒否され、本番のリフレッシュと開発 HMR が外部状態に対して検証されるようになった。

## 概要

このセッションはポート 3081 の DeepSeek Harness Web GUI 内で実行されており、その選択されたワークスペースは空の `test/` ディレクトリだった。モデルへのリクエストは GUI もそのソースチェックアウト、URL、プロセス、更新モードも名指ししていなかった。リポジトリの機能群は Vite 開発スクリプト付きの `apps/web` を公開していたが、完全なブラウザー構成は `dsh web` の背後にあった。

結果として行われた行為は個々にはもっともらしかったが、単一の受け入れターゲットを共有していなかった。ソース編集、ビルド成功、HTTP 200、注入されたブートマニフェスト、ユーザーの既存ページが、互換可能な事実として扱われた。

証拠の出所は `session-3eb796c2-5159-4686-affe-df8719f6f987` の永続化されたイベントログであり、そのヘッダーは作業ディレクトリ `/Users/tn.shen/Documents/deepseek-harness-gui-master/test` を記録している。最初のリクエストヘッダーはシーケンス 6 である。ユーザーへのハンドオフ、素の Vite の起動、代替ホストの起動、ブートマニフェストのプローブ、最初の 3081 プロセスプローブはそれぞれシーケンス 30939、31865、34309、34441、34681 である。以下のタイムラインは、後の報告から意図を再構成するのではなく、これらのイベントに従う。

## 影響

ユーザーは 3 つの連続する誤りを特定しなければならなかった。受け入れ検証がユーザー側に委任されたこと、提案されたプレビューが空白ページだったこと、報告された成功 URL がユーザーの使用中のページではなかったことである。また、管理外の代替サーバーが、ユーザーがそれに異議を唱えるまでターンを超えて存続した。

この調査におけるどの変更も、読み取り専用の 3081 および 3082 のトライアルサービスを再起動または変更しなかった。

## タイムライン

- ターン 2 で、テーマの編集後、エージェントのシーケンス 30939 のメッセージはユーザーに `pnpm run demo:tui` を実行するか、指定されていない Web アプリケーションを開くよう伝えた。組み立て済み Web の受け入れ検証は一切実行しなかった。
- ターン 3 で、エージェントは `apps/web/package.json` を読み、シーケンス 31865 でポート 5173 に素の Vite を起動し、HTTP 200 を観測して成功を宣言した。しかしブラウザーは `client-modules: window.__DSH_BOOT__ is missing or not an object` を送出し、白いページをレンダリングしていた。
- ターン 4 で、エージェントは完全な `dsh web` 経路を見つけ、シェルを再ビルドし、シーケンス 34309 でポート 3334 に管理外のプロセスを起動し、シーケンス 34441 でこの代替がブートマニフェスト付きで 200 を返すことだけを確認した。ポート 3081 は一度もプローブしなかった。
- ターン 5 で、ユーザーはシーケンス 34556 で 3081 がすでに新しいテーマを表示していると報告した。その時になって初めて、シーケンス 34681 でエージェントは既存のプロセスを検査し、冗長なサーバーを削除した。

## 根本原因

Web アセンブリには、現在の GUI、正規 URL、ランタイムモードに関するモデル可視の識別情報がなかった。セッションの作業ディレクトリはユーザーが選択したワークスペースを正しく識別していたが、モデルはそのプロジェクトディレクトリをアプリケーションディレクトリとして扱った。GUI のソースチェックアウト、ビルド成果物、提供プロセス、ターゲットオリジン、ブラウザー受け入れ検証を関連付ける永続的な記録はなかった。

誤った起動経路が正当に見えたのは、素の Vite が HTTP 200 を返したためである。`window.__DSH_BOOT__` は完全なホストによってのみ注入されるため、トランスポートの準備完了はアプリケーションの準備完了を意味しなかった。最初の回帰テストはこの誤りを別の形で繰り返した。タイムアウトが Vite を kill し、非ゼロ終了のアサーションを満たしてしまったのである。ライブ再現により、この偽陽性が明らかになった。

バックグラウンドプロセスのセマンティクスもシェルの `&` によって迂回されたため、ジョブの同一性、完了通知、回収、クリーンアップが適用されなかった。したがってポート 3334 の検証は、2 つ目のサービスが動作したことだけを証明していた。

## 追加されたガードレール

- Web ランチャーは正規のループバック URL を、ログに記録される `app:web-surface` プロンプトセクションと管理対象の `$DSH_WEB_URL` 環境変数に公開する。
- 本番のガイダンスは、成果物を再ビルドし、リフレッシュ後に既存 URL を検証することを要求する。開発のガイダンスは、HMR レシーバーが常に有効であること、同じチェックアウトでの `pnpm run dev:web` がリフレッシュ不要のリロード用にクライアントプラグインバンドルを再ビルドする一方、シェルと素のパッケージの変更には依然としてリフレッシュが必要であることを説明する。
- `apps/web` のスタンドアロン Vite サーブモードは設定時に拒否される。そのサブプロセステストは自然な終了を証明し、`Server.listen()` を計装して、一時的なバインドが見逃されないようにする。
- 階層化された実経路テストは、CLI リクエスト、本番/開発プロンプトの正確な内容、シェルのランタイムファクト、同一ポートの静的置換、ソースウォッチャーの再ビルド、ホストの stat ポーリング、ページ同一性が変わらない状態でのブラウザー HMR をカバーする。
- PR の証拠には、元の 3081 セッションのスクリーンショットと、実モデルによる GUI の変更前/変更後の実行が保存されている。受け入れ検証は外部のブラウザー、HTTP、プロセス、セッションログの観測によって行われる。

## 教訓

- エージェントはユーザーを導く前に、隠れたランタイム前提条件を知っていなければならない。起動モードはアプリケーションのコンテキストであり、属人的な知識ではない。
- HTTP の準備完了、ビルド成功、ブートマニフェストはそれぞれ別の事実である。受け入れ検証は正確なオリジンを名指しし、そこで要求された変更を外部から観測する。
- 代替サービスは既存ページが変更されたことを証明できない。長時間実行プロセスは、実際に要求された場合に管理されたタスクライフサイクルを使用する。
- 回帰テストは、報告されたメカニズムで失敗できなければならない。プロセスのタイムアウトはフェイルファストと等価ではなく、終了後のポート可用性はそのポートが一度もバインドされなかったことを証明しない。
