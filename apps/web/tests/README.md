# apps/web ブラウザー e2e

日本語 | [English](README.en.md) | [中文](README.zh.md)

これらのテストは実際の Web コンポジションをプロセス内で起動し、実際の HTTP 越しに実際のブラウザーで操作する。Chromium が全レーンを実行し、[モデル・リーズニングピッカーのシナリオ](declared-reasoning.e2e.ts)はネイティブマウスフォーカス動作をカバーするため WebKit でも実行する。[セッションリプレイ復旧](session-replay-reload.e2e.ts)も WebKit で実行し、`fresh-round-trip` 記録と期待出力を書き換えずに共有する。アクティブストリーム中の再読み込み、完了ターンの再読み込み、セッションの再オープンをカバーする。レーンの仕組み（モード・フィクスチャ・ゴールデン・`dsh web` からの意図的なコンポジション差分）は [`scaffold.ts`](scaffold.ts) と[ブラウザー e2e の Agent Note](../../../.agents/notes/implemented/testing/2026-07-24-web-gui-browser-e2e-lane.md)に文書化されている。

ワークスペース依存関係のインストール後、リポジトリルートからブラウザーとシステム依存関係をインストールする:

```sh
pnpm --filter @deepseek-ai/dsh-web-frontend exec playwright install --with-deps chromium webkit
```

Linux では `--with-deps` がシステムパッケージマネージャー経由で依存関係をインストールする。永続 CI VM はイメージ保守でこれらの依存関係を提供しなければならず、CI は[フェイルオーバー手順](../../../.agents/notes/implemented/process/2026-07-26-ci-failover-runbook.md)に従いブラウザーバイナリのみをインストールする。

通常のシナリオは登録済みワークスペースもセッションもない状態から始まり、削除済み既定ワークスペースを記録する耐久マーカーがあるため、明示的なフォルダー選択シナリオは cwd を制御できる。`launchWebScaffold({ firstUse: true })` は起動シナリオ向けに初期化を対象のままにする。

## 完了観測

状態依存のケースはワークスペース・承認・添付・モデルストリームのバリアを使い、可視の中間状態と完了した操作を分ける。モデルピッカー永続化の表明はメニュー終了とは独立に保存済み既定を待つ。詳細の終了はフレーム遷移を待ち、アーカイブ検証はシードされたセッションに明示的なタイトルを付け、再読み込みをまたいでその識別子を追う。[CI テスト信頼性ワークフロー](../../../.agents/skills/dsh-ci-test-reliability/SKILL.md#synchronize-on-state)がこれらの同期規則を所有する。

[アイドル投入ハンドオフ](idle-submission-handoff.e2e.ts)はホストフレームとブラウザー配置を足場の 30 秒ターン完了予算まで待つ。Vitest が足場の破棄を所有するため、リプレイ消費エラーが失敗したシナリオ表明を置き換えることはない。

プラグインマネージャーの切り替えは、ホストのプロファイル書き込みとストアの後続インベントリ読み取り（`aria-checked` を再発行する 2 段階）に `PLUGIN_TOGGLE_SETTLE_MS`（10 秒）まで待つ。その定数の JSDoc が測定された連鎖を記録している。

明示的スクロールは `support.ts` の `scrollIntoView` を使う。古い要素が外れた場合はロケーターを解決し直し、ネイティブスクロールと同じブラウザータスク内で接続を確認する。シナリオはスクロール後も可視性と形状の表明を保持する。

## これらはホスト面のテストである

ホストサービスを直接読むため、ルート `tsconfig.host.json` で型検査され、クライアント集約では検査されない。`ctx.connection`・ホスト `SessionStore`・`ctx.sessionProjectionCache` がそれである。実行時にブラウザーを操作してもファイルがクライアントプログラムの一部になるわけではない。2 つの面は同じキーの下で異なるサービスを持つ Cordis `Context` を統合するため、1 つのプログラムが両方を見ることはできない。これらのファイルをクライアント集約に移すと、すべてのホストサービスアクセスがコンパイル失敗になる。

## ここで `@deepseek-ai/dsh-client-*` をインポートしないこと

クライアントパッケージのインポート（値・型のいずれも）は、その TypeScript プロジェクト全体とそれが参照するすべてのプロジェクトを**ホストビルドグラフ**に引き込む。このレーンは既に一度被害を受けている。4 つのクライアント利用者パッケージが `api/remotes` のクライアント面を参照し、それはホスト tsdown が `@deepseek-ai/dsh-goal/remote` を生成するまでコンパイルできないため、ホストビルド段階が自身の生成物を待つことになった。

シナリオがクライアント所有の定数や純粋関数を必要とするときは、供給元モジュールを指名するコメントアウトされたインポートの隣でここに複写すること。ずれは外れたセレクターや古い複写値として現れる。大きな失敗であり、黙った成功にはならない。`scaffold.ts` はウェルカム通知の名前空間・承認フィールド・バージョン・表明する中文コピーでこの規則に従う。

ビルド済みクライアントハーネスは例外である。`assembled-boot.ts` は `AppWebEntry`・起動マニフェスト型・`RemoteMock` をインポートし、`assembled-remote.ts` はクライアントテストランタイムの既定応答と `RemoteMock` をインポートする。これらのパッケージは実際のシェルをテスト所有のキャリア上で起動するための明示的なプロジェクト参照である。チャットシナリオは `support.ts` で `conversationContextKey` を複写し、クライアント側の所有者からはインポートしない。

これを機械的に強制する仕組みはない。レビューで守ること。
