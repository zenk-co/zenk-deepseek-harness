# Desktop CI 公開

日本語 | [English](README.en.md) | [中文](README.zh.md)

## 概要

完成したパッケージを、そのインストーラーを再度ダウンロードすることなく元のマシンから公開する。test と production の両方がバイナリを公開し、続いて更新 YAML を公開する。両デプロイメントとも GitHub Environment の承認を必要とする。GitHub App タグを作成するのは production のみである。実際の COS、CDN、管理者権限による受け入れはデプロイメントチェックのままであり、ローカルフィクスチャがそれらの権限を確立することはない。

## マシンのセットアップ

`DSH_PACKAGING_CONFIG_DIR` は既存のマシンパッケージングディレクトリを指したままにする。完了した試行は兄弟ディレクトリ `releases/<run-id>/<attempt>/` にコピーされる。`DSH_DESKTOP_RELEASES_DIR` はそのルートを絶対パスで上書きする。インベントリにはインストーラー、更新アーカイブ、ブロックマップ、完了メタデータ、およびクレデンシャルを含まないマニフェストが含まれる。デバッグパッケージは保持されるが公開できない。コピーは試行ディレクトリが可視になる前に検証され、既存の試行は置き換えられない。GitHub は同じファイルインベントリを 14 日間保持する。ローカルファイルはオペレーターが削除するまで残る。検証または公開中の試行を削除しないこと。

設定ディレクトリの下に `publishing/test.json` を作成し、認可されている場合は `publishing/production.json` も作成する。各ファイルは `bucket`、パスを含まない HTTPS の `origin`、および絶対 `credentialsFile` を宣言する。クレデンシャルファイルには `secretId` と `secretKey` のみを含める。macOS ではさらに `macOS.signingIdentity` と `macOS.teamId` が必要で、Windows では `windows.certificateThumbprint` が必要である。production は正確な origin `https://download.deepseek.com` と `githubApp.clientId`、および絶対 `githubApp.privateKeyFile` を必要とする。これらのファイルは Git の外に置く。アップローダーがサポートするのは永続 COS クレデンシャルであり、STS セッションクレデンシャルではない。管理者は test と production のバケットを非バージョン管理 (有効でも一時停止でもない) に保たなければならない。公開はこのデプロイメント前提を仮定し、`GetBucketVersioning` を呼び出したり、その権限を要求したりしない。不変バイナリの PUT は `x-cos-forbid-overwrite` を保持する。その保護は、管理者がバケット構成を維持することに依存する。

リポジトリ変数 `DESKTOP_PUBLISH_RUNNERS` を、登録済みランナー名から一意のラベルとターゲットへの JSON マッピングに設定する (例: `{"mini":{"label":"dsh-mini-publish","target":"mac-arm64"}}`)。そのラベルはまさにそのランナーに割り当てる。Windows はターゲット `win-x64` を使用する。ルーティングジョブは元の成功したジョブをチェックし、パブリッシャーは自身のランナー名を記録された名前と照合する。マシン間に共有ファイルシステムや相互の LAN 接続は不要である。

管理者は `desktop-test` と `desktop-production` を作成する必要があり、それぞれに必須レビュアーと許可された `master` デプロイブランチを設定する。ワークフローはいずれかのデプロイメントのレビュアーをチェックする。test は自己承認を許可できる。GitHub App にはこのリポジトリへのインストールアクセスと Contents 書き込み権限、さらに `desktop-v*` タグルールセットの下でリリースタグを作成する権限が必要である。レビュアーの承認がレビュアーのタグ権限を App に移転することはない。設定が欠けている場合は公開が停止する。パーソナルトークンへのフォールバックは存在しない。App アクションは短命トークンを作成し、後に取り消す。ローカル秘密鍵と COS クレデンシャルファイルは、公開アカウントのファイルシステム権限で保護する。トークンアクションはキー内容を受け取るので、マスクされた PEM はジョブ中にランナーの一時的な `GITHUB_OUTPUT` ファイルも通過する。マスキングが隠すのはログであり、ローカルファイルへのアクセスではない。

Environment の承認がゲートするのはこのワークフローであり、同じマシンアカウントで実行される任意のコードではない。アカウント分離と強制ソースブランチ制限は別個の運用作業である。既存の release Environment は変更しないこと。test ジョブは独自のレビュアーを使用し、実際のリリースタグを作成することはない。ローカルのシミュレートされたトランスポートは、App 権限を検証せずにタグ作成とリカバリーを試す。

## パッケージ化と公開

test または production への公開では、Windows は `signing=signed` を選択するか、macOS は **Skip notarization** をオフのままにする。署名なしおよび公証なしのパッケージは内部デバッグ専用であり、公開や自動更新の提供はできない。依存関係をインストールする前に、ホスト側のルーティングジョブが、選択された run と attempt によって特定されるデバッグアーティファクトを拒否する。欠落したアーティファクトメタデータは適格性を確立しない。元のマシンは引き続き保持されたマニフェストと署名を検証する。デバッグパッケージの拒否には、新しい署名済み/公証済みパッケージとその run ID / attempt が必要である。公開の再試行で既存のバイト列を適格にすることはできない。

プラットフォームの `Package Desktop` ワークフロー、プリセット、ソース、チャネル、バージョンモードを選択する。`source_ref` は、test ではリポジトリのブランチ名 (例 `feature/desktop-update`) または `dsh-v*` タグを受け付ける。production は `master` または `dsh-v*` タグのみを受け付ける。`dsh-v` に続いて数字と、英字、数字、ドット、ハイフンが続く名前は、ブランチにその名前があってもタグとして扱われる。タグは選択された製品バージョンと一致しなければならない。パッケージングワークフローは `master` からディスパッチし、ソースを別途入力することを推奨する。生のコミット SHA、PR ref、フォークリポジトリはサポートされない。選択されたソースは CI アダプターを含んでいなければならないので、古いソースは依存関係のインストール前に失敗する。信頼できるブランチのみを選択すること: そのビルドコードは署名マシン上で実行される。これは運用上の規約であり、強制されるワークフロー起点やクレデンシャル分離ではない。公開は記録されたコミットを使用し、それが選択されたブランチ履歴に残っていることを要求する。通常のブランチ前進は許可され、削除や分岐する force-push は拒否される。タグ公開は、タグが依然として記録されたコミットを解決することを要求する。パブリッシャーは `master` からディスパッチする。そのホスト側ルーティングジョブは、元のマシンをスケジュールする前に他の ref を拒否する。パッケージ化されたソースコミットは別途記録される。`version_mode=default` は production では product を、test では auto を選択する。product は選択されたチェックアウトバージョンを保持し、auto は日付/run/attempt を付加し、manual は `build_version` を要求する。latest パッケージは安定バージョンを要求するので、test/latest には product または安定した manual バージョンが必要である。任意の `test_release_id` は test URL プレフィックスである: 空欄はマシンの既定値を保持し、そのプラットフォームでの連続するアップグレードテストは同じ値を必要とし、既定値は定期的にローテーションすべきである。これは GitHub run ID ではない。その検証とローテーションの制限については[パッケージング設定](../../packaging/README.md#configuration-and-local-builds)を参照。

パッケージングはファイルを保持するだけである。成功後、`master` で **Publish Desktop · COS → Run workflow** を開き、パッケージング run URL から `package_run_id` を入力し、任意で `package_run_attempt` を入力する。空欄は最新の attempt を選択し、それは成功していなければならない。古い成功にフォールバックすることはない。明示的な attempt はその正確な成功ビルドを選択する。Windows は署名済みでなければならず、macOS は公証とステープリングを完了していなければならない。GitHub ジョブの証拠が元のランナーを選択し、そのローカルマニフェストが承認前にプリセット、バージョン、ソース、チャネルを提供する。インストーラーやリクエストアーティファクトはダウンロードされない。古い `publishRequested=false` フラグを持つ保持済みパッケージも適格なままである。ローカルファイルの欠落や変更は公開を停止させる。

アップロード前に、パブリッシャーは保持されたすべてのファイルをハッシュ化し、バージョンと宛先のメタデータをチェックし、プラットフォーム署名を再チェックする。macOS は DMG を検証し、ZIP を展開してアプリのチケットを検証する。Windows は Authenticode、構成された署名者サムプリント、タイムスタンプをチェックする。準備は、バージョン、チャネル、プラットフォーム、デプロイメントのフィールドを分けた中国語の承認サマリー、保持された test リリース ID、完全なインストーラー/フィード URL、元のパッケージング試行へのリンク、ソース ref/SHA、プラットフォーム検証結果、提案タグを書き出す。折りたたまれた詳細には COS バケットと、アップロードバイト列 (書き換えられた YAML を含む) のファイルサイズ/SHA-256 が含まれる。公開リポジトリのサマリーは test プレフィックスとダウンロード URL を公開するが、プレフィックスは認証ではない。両方の公開ジョブは **Review deployments → Approve and deploy** を待ち、その後、承認されたマニフェストとアップロード plan ダイジェストを再チェックする。バイト列や宛先が変わっていれば拒否される。承認はバージョンを編集できない。拒否して再ビルドする。両デプロイメントは欠落したバイナリをアップロードし、リモートのバイト列を検証し、その後 YAML を更新する。このワークフローにファイルのみのモードはない。production は最後に、記録されたパッケージングコミットで `desktop-v<version>` を作成する。既存のタグは同じコミットを指していなければならない。

## リカバリーと記録

失敗を解決した後は、失敗した公開ジョブを再実行して準備済みのパッケージ試行を保つか、明示的な元のパッケージ run と attempt を指定して新しい公開を開始する。空欄の attempt で全ジョブを再実行すると、最新のパッケージ試行が再度解決され、新しい承認が必要になる。アップロードを再試行するためだけに再ビルドしないこと。欠落したオブジェクトはアップロードされ、同一のオブジェクトはスキップされ、同名で競合するバイト列は操作を停止させる。不明な書き込み結果はリモートバイト列の読み取りで調整される。より新しいチャネルバージョンは、古いアップロードがそれを置き換えるのを防ぐ。各パッケージは自身に埋め込まれたチャネルのみを更新する: nightly は `nightly.yml` / `nightly-mac.yml` を書き、latest は `latest.yml` / `latest-mac.yml` を書く。latest バイナリはターゲットバイナリプレフィックス下の `latest/` サブディレクトリを使用し、既存の nightly オブジェクトとは分離される。同じソース/バージョンを両方のチャネルに公開するには 2 つのパッケージが必要である。既存のリリースタグは同じソースコミットに対してのみ再利用される。

兄弟の `upload-records/` ディレクトリは、操作 ID、改行区切りのイベント、終端結果を保持する。フィード書き込みインテントは、以前の YAML と要求された YAML の両方を保持する。失敗はそのステージ、安全なエラー分類、診断を記録する。COS の失敗はさらに `GetObject` または `PutObject` を識別し、利用可能な場合は検証済みの HTTP ステータスとリクエスト ID も記録する。アクセス拒否のレポートは検査すべき権限を明示する。生のプロバイダー応答とクレデンシャルは除外される。監査の初期化は、そのファイルが完成した後にのみ可視になる。放棄された `.initializing-*` ディレクトリが、完了した公開のためにスキャンされることはない。書き込みと読み戻しは続行前に記録される。終端結果の欠落は成功ではなく中断を意味する。Actions も操作記録を診断アーティファクトとして 30 日間保持する。これらのローカル記録は改ざん防止ではない。COS の読み戻しはストレージバイト列を検証するものであり、公開 CDN の挙動を検証するものではない。公開ダウンロードの受け入れは別である。

フィードが完了したがタグ付けが失敗した場合、結果は `published-tag-pending` となり、ジョブは目に見える形で失敗する。再試行時、永続的なフィード完了の証拠はタグのリカバリーのみを許可し、後続のリリースがチャネルを前進させていても変わらない。古い YAML を再公開することは決してない。既存の競合するタグは管理者による調査を要し、自動的に移動されることは決してない。

通常の公開と手動の復元は同じローカルチャネルロックを取得する。クラッシュすると兄弟 `publish-locks/` の下にロックディレクトリが残ることがある。手動で削除する前に、ライターが実行されていないことを確認する。ランナーラベルだけでは、他のマシン上のライターを調整できない。チャネルごとに公開マシンを 1 台に保ち、移行時にはその記録を保持する。

## チャネルの復元

公開マシン上で、リポジトリスクリプト `apps/desktop/scripts/rollback-desktop-channel.ts` を `node --import tsx` 経由で実行する。`GITHUB_REPOSITORY`、`RUNNER_NAME`、`DSH_PACKAGING_CONFIG_DIR`、`DESKTOP_PUBLISH_ROUTE` は元のパッケージコンテキストのままにしておく。route JSON には `runId`、`attempt`、`commit`、`runnerName`、`target`、`preset`、`sourceRef`、`channel` が含まれ、保持されたマニフェストのソースフィールドで利用できる。`--record` にはその成功した公開の監査ディレクトリを、`--expected-version` には現在オンラインのバージョンを、`--reason` には運用上の理由を渡す。

`--execute` なしでは、スクリプトはリモートオブジェクトを読み取り、正確な YAML 変更を書き込みなしで出力する。プレビューには COS 読み取りクレデンシャルが必要である。`--execute` ありでは、歴史的ファイルを検証し、新しい監査レコードに before/after YAML を保存し、現在のチャネルを再チェックし、YAML のみを復元する。バイナリのアップロードもタグの変更も行わない。ターゲットバイト列にすでに一致するチャネルはスキップされる。他のチャネルは期待される現在バージョンと一致しなければならない。これにより、中断前に 1 つのフィードが復元された後のリカバリーが可能になる。現在のバージョンが異なる場合は操作が中止される。復元はマルチオブジェクトトランザクションではない。部分的な失敗の後は、続行前に監査を検査する。

Desktop クライアントは自動ダウングレードを無効にする。古いフィードの復元は、追加のクライアントが不良リリースを受信するのを止められる。すでにより新しいバージョンにいるクライアントはダウングレードしない。より高いバージョンの修正リリースは別のリカバリー経路である。
