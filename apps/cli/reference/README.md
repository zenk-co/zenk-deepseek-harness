# `dsh` CLI 動作リファレンス

日本語 | [English](README.en.md) | [中文](README.zh.md)

このリファレンスは、プロファイル、プラグイン管理、設定ダンプのコマンドモードを定義します。Argv は [`src/args.ts`](../src/args.ts) を通じて一度だけ解析され、[`src/bin.ts`](../src/bin.ts) は選択されたランナーのみを動的にインポートします。

[生成済みコマンドヘルプ](../../../docs/cli-help.md)には、ランチャー、プラグイン管理、出荷プロファイルの完全なヘルプが含まれています。更新には `pnpm run gen-cli-help` を実行し、`pnpm run verify-cli-help` で現在の CLI との一致を検査します。

## プロファイル起動

`dsh <name>` は `dsh --profile <name>` の省略形であり、`$DSH_HOME/profiles/<name>` にあるプロファイルを起動します。短縮名は `dsh` の直後に置かなければなりません。`plugin` はプラグイン管理コマンドのままなので、その名前のプロファイルを起動する場合は `dsh --profile plugin` を使います。有効なツリーは、空のルートに対して次の順序で適用して構成されます。プロファイルマニフェストの `dsh.profile.bundles` リストに挙げられた各バンドルパッチ、プロファイル自身の `cordis.patch.yml`、ホームレベルの `$DSH_HOME/cordis.patch.yml`（すべてのプロファイルで共有されるマシンローカルな設定であり、プロファイル単位の層より上位になります）、および argv 順の各 `--patch <path>` オーバーレイです。後の層が行単位で優先され、パッチはキーをディープマージするのではなく対象行の `config` 値全体を置換し、新しい行を挿入することもできます。最終的な YAML 構成が `dsh-hmr` が設定を監視するかどうかを制御し、HMR がなければ変更には再起動が必要です。解析、スキーマ、解決、またはプラグイン起動の失敗は報告され、非ゼロで終了します。SIGINT と SIGTERM は終了前にマウント済みルートを破棄します。

バンドル名は、まず dsh インストール先から解決され、次にプロファイルディレクトリから解決されます。インボックスバンドル（`@deepseek-ai/dsh-base`、`@deepseek-ai/dsh-web-app`、`@deepseek-ai/dsh-headless`、`@deepseek-ai/dsh-sdk-app`、`@deepseek-ai/dsh-sdk-minimal`、`@deepseek-ai/dsh-acp-app`）はしたがって常に実行中の `dsh` と同じインストール先から取得され、ツリー外バンドルはプロファイルの pnpm 管理下にある `node_modules` から取得されます。行をマウントする前に、ランチャーはインストール先と選択されたバンドルをその順序で走査し、得られた不変のランタイム解決を Node のリゾルバーに組み込みます。起動時に共有またはプロファイル所有のフォールバックリンクは作成されません。プロファイルにインストールされたパッケージはネイティブの優先順位を保ち、プロファイル初期化とパッケージマネージャーの書き込みはランタイム解決から分離されたままです。

`web`、`headless`、`sdk`、`sdk-minimal`、`acp` プロファイルは、初回使用時に出荷テンプレートから自動初期化されます（`web` は base + web-app でライブパッチ付き、`headless` は base + headless で起動時限定パッチ付き、`sdk` は base + sdk-app で起動時限定パッチ付き、`sdk-minimal` は単独バンドルで起動時限定パッチ付き、`acp` は base + acp-app で起動時限定パッチ付き）。その他の存在しないプロファイルは、`dsh plugin --profile <name> add <package>` の実行を促すヒントとともに明示的に失敗します。

`dsh --profile <name> --from-default-profile <template>` は、起動前にカスタムのターゲットを5つの出荷テンプレートのいずれかの新しいコピーで置換します。ターゲット名には、いかなる文字の大文字小文字であっても出荷プロファイル名は使えません。ランチャーはターゲットの隣にステージングディレクトリを用意して新しいプロファイルを組み立て、所定の場所に移動してから、インストール済み依存関係やユーザーパッチを含む以前のターゲットディレクトリを削除します。移動に失敗すると以前のディレクトリが復元されます。復元にも失敗した場合や、2回のリネーム処理の途中でプロセスが停止した場合は、以前のディレクトリは手動復旧用に `$DSH_HOME/profiles/.<name>.staging-*/previous` に残ります。複数のプロセスが同じターゲットを同時に置換する場合、少なくとも1つは成功し、ターゲットには完全なコピーが1つ保持されます。このコピーは、テンプレートの現在のバンドルリストを、依存関係が空でユーザーパッチが空の新しいマニフェストに保持します。`<template>` で指定されたローカルプロファイルの読み取り、その依存関係やパッチのコピー、継承フィールドの保持は行わず、後のテンプレートリスト変更で新しいプロファイルが書き換えられることもありません。コピーされたリストに挙げられたインボックスバンドルは、現在の dsh インストール先から解決されます。置換が成功してもランチャーの出力は追加されません。

オプションを省略すると、リセットせずにプロファイルを起動します。不明なテンプレートや出荷済みのターゲット名は、ターゲットが変更される前に失敗します。不明テンプレートの診断では有効なテンプレート名が示されます。置換はバンドル解決とアプリケーション起動より前に確定するため、後の失敗があっても新しいプロファイルはディスクに残ります。3つの設定ダンプモードはいずれもこのオプションを受け付け、ターゲットを起動せずに置換します。

```sh
dsh rescue --from-default-profile web
dsh rescue
```

### アプリ引数

ランチャーのフラグは先頭に置き、認識できない最初のトークンで終わります。そこから後ろはすべて `ctx.cmdlineArgs` を通じて起動済みプロファイルにそのまま渡され、挿入されたアプリプラグインが解析できます（[`dsh-cmdline`](../../../packages/boot/cmdline/README.md)）。したがって `dsh rescue --from-default-profile web --no-open` は `--no-open` を Web に渡す前に rescue をリセットし、`dsh --profile web --port 8080` は Web アプリの `--port` に届き、`dsh --profile web --help` はそのアプリのヘルプを表示して何も起動せず、`dsh --help`（渡し先のプロファイルがない場合）はランチャー自身のヘルプを表示します。`-V`/`--version` は、アプリ引数境界より前に現れた場合にランチャーのバージョンを表示します。

コンポジションは一度だけマウントされます。通常のプラグインは `cmdlineArgs` を挿入し、このアプリの引数を解析して、解決結果をサービスとして提供します。フラグから構成された各行はそのサービスを挿入し、Loader はその行の設定を評価する前にそれを待ちます（`port: !!js ctx.webStartup.port ?? 3080`）。したがってフラグは横に書かれた値より優先されます。この優先関係には、その行が当該の式を保持していることが必要であり、全体の `config` をリテラルで置換するユーザーパッチはランタイム読み取りを除去します。ヘルプと拒否された引数は、プロバイダーのサービスに依存する行を有効化せずに終了を要求します。拒否は非ゼロ、ヘルプは 0 です。HMR 有効時、パッチファイルの編集は起動中のサービスに対して式を再評価するため、提供中のポートをリセットできません。

ランチャーフラグはアプリ引数より前に置かなければならず、ランチャーのパーサーは1つの `--` を消費します。リテラルの `--` として届ける必要があるアプリ引数には `-- --` が必要です。`plugin` がプラグイン管理を選択するのは `dsh` の直後に置かれた場合のみであり、プロファイル選択後の `plugin` や `web` は通常のアプリ引数です。アプリ引数より前の `--profile` オプションの繰り返しは、短縮名の後の明示的オプションを含めて拒否されます。`ctx.cmdlineArgs.get()` は共有の不変読み取りであり、複数のプラグインが同じスナップショットを解析でき、リーダーのいないプロファイルはアプリ引数を無視します。

出荷アプリのコマンドラインは次のとおりです。

| プロファイル | 引数 |
|---|---|
| `web` | `--host`、`--port`、`--tls-cert`、`--tls-key`、`--public-url`、繰り返し可能な `--trusted-host`、`--no-open` |
| `headless` | タスクテキスト（位置引数として） |
| `sdk` | オプションなし。stdio が JSON-RPC プロトコルを運ぶ |
| `sdk-minimal` | オプションなし。stdio が同じ JSON-RPC プロトコルを運ぶ |
| `acp` | オプションなし。stdio が ACP（Agent Client Protocol）を運ぶ |

ワンショットタスク（`dsh --profile headless "run the tests"`）は、コアレジストリを通じて1つの新しい永続化エージェントを作成し、タスクを投入して静止を待ってからセッションをフラッシュし、その durable interval から最後の空でないアシスタントテキストと最終 `turn/end` 理由を導出します。空でないプロバイダー推論差分を `dsh: reasoning:` 見出し付きで stderr にストリーミングし、stdout には最終テキストのみを表示して、`completed` なら 0、それ以外は 1 で終了します。推論のない成功応答では stderr は空のままです。タスクなしの呼び出しはそのアプリの使用法エラーです。出荷 headless プロファイルはブラウザー Connection、HTTP サーバー、Web ランタイム、ブラウザークライアントをマウントせず、待受ポートも開きません。

構成済みツリーを起動せずに検査します。

```sh
dsh --profile web --dump-default-config
dsh --profile web --patch ./extra.yml --dump-config
```

`--dump-default-config` はバンドル層のみを表示し、`--dump-config` はプロファイルの `cordis.patch.yml`、ホームレベルの `$DSH_HOME/cordis.patch.yml`、`--patch` オーバーレイを追加します。どちらも各行を提供したファイルとそれを変更したすべてのオーバーレイを名指しするコメントを表示します。`!!js` 式は未評価のままであり、挿入行内の相対プラグイン名はそのパッチファイルの隣で解決され、不一致のパッチ対象は stderr に報告されます。ダンプは存在しないプロファイルファイルを初期化します。アプリコマンドラインプロバイダーを実行しないため、アプリ引数が解決される前の構成済みツリーを表示し、アプリ引数を伴う呼び出しを拒否します。

<a id="config-schema-dump"></a>
### 設定スキーマダンプ

`--dump-config-schema` は、繰り返し可能な `--patch` と `--from-default-profile` を含め、`--dump-config` と同じバンドル、プロファイル、ホーム、argv パッチ層を使います。3つのダンプフラグは相互に排他的であり、アプリ引数と予約済み `desktop` プロファイルを拒否します。構成に成功すると、整形済み JSON Schema 2020-12 ドキュメント1件を stdout に出力します。そのルートは `--dump-config` が表示する解析済みエントリーリストを記述し、`$defs.patchList` はプロファイル／ホーム／CLI オーバーレイを別途記述します。そのフラグメントを検証する際はドキュメントの `$defs` を保持してください。準備、パッチ解析／構成、または解決セットアップの失敗は、スキーマなしで非ゼロ終了します。収集および投影の失敗は部分出力を保持して終了コード 1 で終了し、診断は stderr にも表示されます。これには、stdout に有効で有用なスキーマが含まれる場合でも `partial` 投影や省略された非 JSON アノテーションが含まれます。スキーマダンプの不一致対象警告には層ラベルが付きません。発生源ラベル付き警告には同じ層で `--dump-config` を使ってください。

プラグイン設定フィールド、デフォルト、説明、サポートされる制約は、ネイティブ Schemastery 宣言から投影されます。通常フィールドはインラインであり、共有設定と再帰は `$ref` を使います。JSON Schema のデフォルトはアノテーションであり、デフォルト挿入ではありません。必須フィールドは、Schemastery の nullable フォールバックが検証を通過できるかどうかを考慮します。ユニオンは `anyOf` を使いますが、ネイティブ実行は最初の成功ブランチを選択します。`secret`、`credential-ref`、`ms` などのロールメタデータと `volatile` ライブ更新メタデータは `x-cordis` アノテーションに残ります。不正な volatile 包含はスキーマ定義エラーであり、フィールド入力型は参照オブジェクト型になりません。コールバック検証、未対応の正規表現セマンティクス、その他の未投影制約は、黙って破棄せず partial として印付けされます。非有限境界と非 JSON デフォルト／表示アノテーションは、構造フィールドを利用可能に保ちながら制限付きで省略されます。オブジェクト定数は通常の nullable メンバー制約を保持しますが、継承プロパティ比較は partial として印付けされます。表現不能なデフォルト、未対応のインターセクション、未解決の再帰デフォルト依存は不明省略動作を保持し、ネイティブ検証が依然として必要です。

YAML は Cordis エントリーリスト方言で解析します。`!!js` スカラーは不活性な `{ "__jsExpr": "..." }` マーカーになります。通常の設定値とエントリー `disabled` は結果を評価せずにこれらのマーカーを受け付けます。グループリストと Include フィールドはリテラルのままです。エントリー id は任意であり、空でない id のない非挿入パッチは Loader 警告付きの no-op として受け付けられます。無効化されたエントリーは、`group: true` が有効化を強制しない限り必須設定を省略でき、無効化式も省略可否をランタイムまで未定にします。提供された設定値は依然として検証されます。`disabled` は真偽値、null、式マーカーを受け付け、Loader が強制変換するその他の truthy 値は拒否されます。`group: true` のない無効化グループや include の子は、Loader が生成しないため検証されません。無効化された `group: true` 行配下の子や無効化グループへのパッチ挿入は有効として検証されますが、Loader は先祖無効化された子を未初期化のままにします。既知のルートツリー対象は、深い部分オブジェクトではなく設定全体の置換を検証します。以前のパッチで導入・変更された include ローカル id や順序依存対象は推測されません。不明なプラグイン名はオープンのままであり、1つの名前に対する異なる解決は曖昧さ診断付きユニオンを使います。

ルート `x-cordis` アノテーションは `profile`、`complete`、`entries`、`diagnostics`、`patchSchema` を含みます。エントリーは `path`、任意の `id`、`name`、`status`、`configRef` とともに走査順を保持し、ステータスは `schema`、`partial`、`absent`、`unsupported`、`error` です。任意の `tree: "group" | "include"` はネイティブキャリアーを識別します。設定が出力されないため `status: "absent"` になり得ますが、`configRef` は Loader 構造定義を指します。不正形式の検査行は、有効な兄弟を破棄せずに位置付きエラーを受領し、リテラル名が存在しない場合 `name` は省略されます。不正なリストコンテナーや include パッチ構成失敗はキャリアーレベルの診断を生成し、構成失敗ではパッチ未適用やフィルター済みの子を最終として報告するのではなく、その include の子を利用不能のままにします。`group: true` のない無効化キャリアーは設定を省略でき、子なしツリーとして記録されます。投影制限はその設定を共有するすべてのエントリーで繰り返されます。欠落設定は禁止構成ではなく不明フィールドを意味します。検出パスはグループ子に `/config/<index>`、include 子に `/include/<index>` を追加し、後者はルートダンプへの JSON ポインターではありません。`complete` は、エラー診断、`partial`／`unsupported`／`error` エントリー、または1つのプラグイン名が複数の設定定義に対応する場合に false です。このリファレンスは無効化行を含む宣言を対象とします。それらのインポートや include 失敗により起動可能なプロファイルが不完全になり得ます。ランタイム生成のプリセット／クライアントツリーやプラグイン起動検査はこのリファレンスの範囲外であり、逆に `complete` は起動成功を保証しません。

先行ユニオンブランチが入力を変更し得る場合や、名前変更／衝突し得る辞書キーは緩和検証を要します。遅延メタデータ伝搬は現在の設定を超えた共有ノードに影響し得るため、その設定はネイティブ変更を模擬するのではなく、利用可能な宣言詳細を無制限の代替とともに保持します。これらの場合は partial であり、ネイティブ検証が必要です。

収集は信頼済みモジュールをインポートし、設定ゲッターや遅延ビルダーを呼び出すことがありますが、プラグイン適用、変換コールバック実行、設定式評価は行いません。インポートは出力前後にブロックしたりプロセスハンドルを保持したりできるため、自動化呼び出し側は外部タイムアウトを強制すべきです。ダンプは強制終了せず、インポート時リソースの破棄も所有しません。通常のインポート／ビルダー stdout は stderr に振り分けられ、ファイルディスクリプターへの直接書き込みは傍受されません。プロファイル準備は YAML ダンプ初期化書き込みを保持します。実際の設定値ではなくスキーマ宣言のみが出力されますが、宣言済みデフォルトや生プラグインエラーには機密データが含まれ得ます。共有前に出力を確認してください。コレクター API は [app-boot](../../../packages/boot/app-boot/README.md) を参照してください。

出力はバージョン付き永続カタログではなく、再生成される pre-stable リファレンスとして扱ってください。`$schema` は JSON Schema 検証方言を識別し、`x-cordis` は dsh リリースに従います。dsh やプラグイン変更後は再生成し、定義名、順序、テキストをハードコードせず `$ref` と `configRef` に従ってください。非互換な方言変更は新しい `$schema` を選択し、アノテーション変更にセッション形式マイグレーションは使いません。

<a id="startup-diagnostics"></a>
## 起動診断

必須プラグイン有効化失敗では、失敗したプラグインとその元のスタック、続いて保留中プラグインと不足サービスを表示します。必須プラグインは保留リストの先頭に表示されます。最終 `Full diagnostics:` 行は、`$DSH_HOME/logs/`（既定 `~/.dsh/logs/`）直下の一意な `startup-<timestamp>-<uuid>.log` ファイルを名指しします。CLI は、プラグインハンドルが開いたままでも、コード 1 で明示的に終了する前にレポートと stderr 書き込みを完了します。以前のレポートを上書きしたり自動削除したりしません。

レポートには DSH と Node のバージョン、プラットフォーム、プロファイル、ルート設定パス、すべての非活性プラグインのモジュールと状態、元のエラー、起動警告／エラー引数が含まれ、Fiber のないインポートエラーも含みます。Node 検査は、深さ・文字列・配列制限を無効にして、入れ子原因、集約メンバー、循環参照、非列挙プロパティ、Symbol プロパティを保持します。カスタムインスペクターは無効であり、アクセサーは評価せずに記述されます。コレクターは非同期失敗クリーンアップを含み、起動が落ち着いたら停止します。記録済みエラーと独立に環境変数や設定内容を収集しません。生プラグインエラーには設定値や認証情報が含まれ得るため、レポートヘッダーは共有前の確認を読者に警告します。値は編集されません。

新しいディレクトリとファイルは POSIX 上でモード `0700` と `0600` を要求します。CLI は書き込み成功後にのみファイルパスを表示します。ログディレクトリやファイルに書き込めない場合、stderr に書き込みエラーと完全なレポートが含まれ、終了コードは 1 のままです。任意のみの有効化警告はレポートを作成せず通常出力を保持します。

## プラグイン管理

`dsh plugin --profile <name> <args...>` は、存在しないプロファイルを初期化してから（出荷テンプレート、またはその他の名前には `@deepseek-ai/dsh-base` 単体）、プロファイルディレクトリを作業ディレクトリとして `<args...>` を `pnpm` に転送します。`add`、`remove`、`why`、`update` やその他の pnpm 動詞はすべてそのまま動作します。pnpm は PATH 上になければなりません。相対パス指定（`.`、`../plugin` とそれらの `file:`／`link:` 形式）はまず呼び出しディレクトリを基準にするため、プラグインチェックアウトからの `add .` はプロファイルではなくそのチェックアウトをインストールします。成功するたびに、`dsh.profile.bundles` はインストール状態と突合されます。マニフェストが `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }` を宣言するパッケージに解決される各依存関係は層スタックに参加し（宣言を獲得した `update` は有効化されます）、バンドルなし依存関係は1回限りの警告付きでプレーンのままとなり、除去された依存関係はスタックを離れます。

`dsh plugin` は転送引数より前でのみ `--profile` を読み取ります。転送引数は認識できない最初のトークンから始まるため、`--profile <name>` を先頭に置きます。転送引数が pnpm コマンドから始まる場合、そのコマンド以降は `-h` や `--help` を含めてすべてそのまま pnpm に届きます。`--filter <selector>` や `-r` などの pnpm オプションから始まる場合、後の `-h` や `--help` は pnpm ではなく転送側のヘルプを表示するため、pnpm のヘルプに届けるにはそれらより前に pnpm コマンドを置きます。転送引数より前の `-h` や `--help` は転送側自身のヘルプを表示して 0 で終了します。

Codex と Claude Code サブエージェントプロバイダーは別々の任意バンドルです。どちらかのパッケージを追加し、1つのコマンドで両方を追加し、またはどちらかを個別に除去します。

```sh
dsh plugin --profile <name> add @deepseek-ai/dsh-subagent-codex
dsh plugin --profile <name> add @deepseek-ai/dsh-subagent-claude-code
dsh plugin --profile <name> add @deepseek-ai/dsh-subagent-codex @deepseek-ai/dsh-subagent-claude-code
dsh plugin --profile <name> remove @deepseek-ai/dsh-subagent-codex
dsh plugin --profile <name> remove @deepseek-ai/dsh-subagent-claude-code
```

成功した pnpm 操作はディスク上のプロファイルマニフェストとバンドルリストを変更します。実行中のプロファイルは現在の起動時のバンドル集合を保持します。バンドル追加・除去・更新後はそのプロファイルを再起動してください。この起動境界はバンドル所属に適用され、プロファイルやホーム `cordis.patch.yml` への通常編集はホットリロードで有効になります。次回起動時、各インストール済みバンドルは休止中のホストプロバイダーのみを登録し、コピーされたプリセットは新しいエージェント向けに対応ツール行を別途有効化しなければなりません。実行ファイル、認証、ペイロード、失敗詳細は [Codex プロバイダー README](../../../packages/subagent/subagent-codex/README.md) と [Claude Code プロバイダー README](../../../packages/subagent/subagent-claude-code/README.md) が所有し、既定依存クロージャーは [base バンドルリファレンス](../../../packages/bundle/base/README.md) が所有します。

```sh
dsh plugin --profile tui add github:deepseek-harness/turtle-ui
dsh plugin --profile tui remove turtle-ui
dsh --profile tui
```

ソース同梱の Git ホストプラグインは、インストール中に `prepare` スクリプトでビルドされます。pnpm ≥10 は利用者が許可するまでこれをブロックするため、最初の `add` は pnpm の `allowBuilds` ヒント（およびプロファイルの `pnpm-workspace.yaml` への dsh ポインター）とともに失敗します。表示されたキーをそこにコピーして再実行してください。ビルド済み tarball やローカルチェックアウトのインストールに許可は不要です。

## Web プロファイル

`dsh web` はプロファイル短縮形を使います。ランチャーフラグが先に解析され、残りのフラグは Web アプリに属して通常バンドルプロバイダーが解析します。`--host` と `--port` は構成済みリスナー値を上書きし、`--tls-cert`／`--tls-key` はリスナーの `tls` ペアを設定します。ホストはワイルドカードではなく具体的なローカルアドレス1件を名指ししなければなりません（`--host 0.0.0.0` は使用法エラーで終了します）。`hostname -i` は複数を列挙し得るため1件を渡してください。繰り返し可能な `--trusted-host` 値は `ctx.webStartup.trustedHosts` に収集され、デプロイ式が独自のオーソリティを追加できます。`--no-open` は今回の呼び出しの既定ブラウザー受け渡しを無効化します。クライアントプラグイン HMR レシーバーは常時マウントされて `pnpm run dev:web` がクライアントバンドルを再ビルドするまで待機します。そのコマンドは一度ビルドしてこの同じランチャーを起動し、クライアントバンドルを再ビルドし続けます。`--no-serve` 付きでは他で起動した `dsh web` の隣でウォッチャーのみを実行します。

`--public-url <url>` は、リスナーのバインドアドレス URL（ループバックバインド時はループバック）の代わりに、HTTP(S) アプリケーションルート1件を、任意の転送プレフィックス付きで告知します。信頼は付与しないため、ブラウザー可視のオーソリティは依然として `--trusted-host` で名指ししなければなりません。前段に置くプロキシが提供すべき内容は [リバースプロキシ背後での Web UI 公開](../../../docs/user/guide/public-deployments.md) に挙げられています。

`--tls-cert <file>` と `--tls-key <file>` は、リスナーに平文 HTTP の代わりに HTTPS を提供させます。両者は1つの設定であり、両方またはなしのいずれかで、それぞれプロセス作業ディレクトリ基準で解決されるファイルを名指しします。証明書ファイルは中間を含む完全なチェーンを保持し、鍵ファイルは暗号化されていない PEM 秘密鍵を保持します。存在しない、読み取れない、空の、または無効なペアは起動を失敗させ、HTTP へのフォールバックは決してありません。キャリアーはファイルを一度だけ読み取り、証明書の取得・更新・監視を行うものがないため、置換ペアはリスナーリロードまたはプロセス再起動後にのみ有効になります。HTTPS も信頼を付与しません。ブラウザーは証明書を信頼してその名前が対象とするオーソリティを開かなければならず、Connection は依然として各リクエストを認証して Host/Origin を検査し、受信リスナーが HTTPS を提供するためセッション Cookie は `Secure` です。既定ポートは 3080 のままであり、`--public-url` は独立した告知のままです。

```sh
dsh web
dsh web --host "$(hostname -i | awk '{print $1}')" --public-url https://app.example/ --trusted-host app.example
dsh web --tls-cert ./server-chain.pem --tls-key ./server-key.pem
dsh web --no-open
dsh web --patch ./extra.cordis.yml
dsh web --dump-config
dsh web --help
```

本番 Web ランナーにはビルド済みパッケージとフロントエンド成果物が必要です（`pnpm run build`）。設定時は告知 `--public-url` を表示し、そうでなければリスナーのスキーム付きバインドアドレス URL を表示します（既定 `http://127.0.0.1:3080`、TLS 設定時は `https://`）。Host/Origin フェンスはバインド IP を直接受け付け、プロキシや DNS オーソリティには依然として `--trusted-host` が必要です。起動行と既定ブラウザー受け渡しは完全な Loader ツリーを待ちます。継承された空でない `SSH_CONNECTION` や `SSH_TTY` は起動行ではなくブラウザー起動を抑制します。ブラウザー受け渡しの直前に `dsh web: opening the default browser; pass --no-open to disable` を表示し、OS 受け渡しに失敗した場合は理由を stderr に名指しして起動 URL を指し示しながらサーバーは動作を続けます。

プロセス終了時はプラグインツリーに最大5秒の破棄猶予を与えます。最初の `SIGINT`／`SIGTERM` がその優雅な排出を開始します。`SIGTERM` はスーパーバイザーの通常停止要求であり、すべての面で 0 終了し、`SIGINT` は 130 を報告します。2回目のシグナルは即時終了を強制します。ワンショットの正常完了が既に破棄で停滞している場合、最初の `Ctrl+C` はエスカレーションとなり、飲み込まれずに直ちに終了します。

base 基盤モードは呼び出しディレクトリを既定ワークスペースルートとして扱い、適用可能な `AGENTS.md` または `CLAUDE.md` 指示を 65,536 バイトの描画予算で読み込み、インメモリー SQLite セッション内容インデックスを使います。単独 `sdk-minimal` プロファイルは呼び出しディレクトリをサンドボックスポリシールートとして使い、`read_image` を含みますが、テキストファイルシステムツール、指示検出、SQLite を省略します。有効な HMR プラグインは両方の `cordis.patch.yml` 層（プロファイルとホーム）を監視して有効な編集をトランザクションで再適用し、HMR がなければプロセスは一度だけ適用します。ワンショット面は有界シャットダウンで終了し、生存ウォッチャーを破棄します。

base 基盤プロファイルの新規セッションは既定で `workspace-write` 許可プリセットになります。Bash とファイルシステム変更はセッションワークスペースとプラットフォーム一時ルートに制限され、読み取りとネットワークアクセスは閉じ込められませんが、プロセス可視性は選択サンドボックスバックエンドに依存します。bwrap はホストプロセスを隠すプライベート PID 名前空間でコマンドを実行し、Landlock と Seatbelt はホストプロセス可視性を変更しません。`DSH_PERMISSION_MODE` はプロセスフォールバックを変更します。保存済み一般設定許可は後の Web セッションに影響し、開封済みセッションには影響しません。単独 `sdk-minimal` ツリーは代わりに `danger-full-access` に固定し、承認や許可設定サービスをマウントしません。

`DSH_TOOLS_MODE` はプロセス向けに `native` または `ptc` を選択し、他の値は起動時に失敗します。出荷 `minimal` エージェントプリセットはそのデプロイ表示を保ち、完全なシステムプロンプトを `You are a helpful software engineer assistant.` に固定し、プラットフォーム選択の永続シェル、`read_image`、`working_directory` を提供します。自動コンテキスト圧縮と人手 `/compact` コマンドをサポートします。Web セッション作成時は 极简模式 を選択してください。共有ブラウザー、ワークスペース、永続化、サンドボックス、許可ホストはそのままです。

## 共有デプロイ動作

base バンドルは、ネイティブ DeepSeek アダプター、設定および認証情報プロバイダー、安定版 `web_search` と `web_fetch`、公開限定 HTTP フェッチプロバイダー、既定オンの DeepSeek セッションログアップロード、全ユーザー向けのフィードバックゲート OTel アップロードをマウントします。プロバイダー認証情報は、継承環境、`$DSH_HOME/.credentials.yaml`、呼び出しディレクトリの `.env`、次に `$DSH_HOME/.env` の順に解決されます。管理ドキュメントが `process.env` に実体化されることはなく、両方の `.env` ファイルは通常の起動環境層です。検索は `DEEPSEEK_API_KEY` を使い、`DEEPSEEK_SEARCH_BASE_URL` を受け付けます。有効なフェッチ呼び出しは、呼び出しごとの確認なしにすべてのサンドボックス・承認モードで実行され、プロバイダーは接続前に非公開宛先を拒否します。Web アプリは base ツール行を無効化し、同じツールを `cordis`、`ptc`、`standard` エージェントプリセット経由で公開します。

フィードバックはモデル作業を開始せずにセッションログに記録されます。[DeepSeek セッションログ寄稿](../../../packages/session/session-log-deepseek/README.md)は、既定で未承認の完全なログ接尾辞を後続 DeepSeek リクエストとともに送信します。設定済みゲートウェイ経由のリクエストも含みます。オプトアウトには Web で **Settings → General → Upload Session Log when using the official model API** をオフにするか、その `enabled` 構成を `false` に設定します。[OTel セッションアップロード](../../../packages/session/session-telemetry-otel/README.md)は、要求ヘッダーなしに `deepseek-official` を含むすべてのユーザーとプロバイダーに適用されます。base の既定は `FEEDBACK_ONLY` であり、新しい自身のテキストフィードバック、メッセージ評価、編集、撤回は、保存済みコンテキストを含む完全な正準プレフィックスをそのイベント経由で解放し、後の記録は次の明示的フィードバックを待ちます。継承された親フィードバックはフォークを承認しません。要求、復元、マウント、HMR は取得を開始しません。SDK バッチ処理は、追加の対話やモデル作業なしに承認済みアップロードを完了できます。`DSH_TELEMETRY_MODE=DISABLED` は OTel 配信を無効化し、`FULL` は拒否され、空でない `DSH_TELEMETRY_DISABLED` はその行を無効化します。`DSH_TELEMETRY_OTLP_URL` はコレクターを選択します。受け渡しはベストエフォートであり、コレクター受領ではありません。durable な outbox や再試行保証はありません。これらの OTel 設定は DeepSeek 寄稿の有効・無効を切り替えません。どちらの経路もモデル入力を変更しませんが、エクスポートにはメッセージテキスト、ツール引数と結果、ワークスペースパスが含まれ得ます。

外部プラグインバンドルは `dsh plugin --profile <name> add <package-or-git-spec>` でインストールします。インストールされたパッケージは自身の依存関係を所有し、宣言済み `cordis.patch.yml` 層を提供します。CLI はパッチ層向け依存関係として `@deepseek-ai/dsh-mcp-client` も同梱しますが、各サーバーコマンドはエージェントサンドボックス外の信頼済み実行コードであるため、既定で有効な MCP サーバーはありません。

## ソース実行

リポジトリルートから、新規チェックアウト後や成果物の更新が必要な際は個別に `pnpm run build` を実行し、その後 `pnpm dsh <args...>` を使います。`package.json` スクリプトは `apps/cli/src/bin.ts` を `node --import tsx/esm` でビルドせずに起動し、すべての引数を転送します。Typert ホスト成果物がない場合、プロファイル起動はビルド指示なしのモジュール解決エラーで失敗します。それらのホスト成果物が存在すれば、不足したフロントエンドやクライアントプラグインバンドルは起動時に `pnpm run build` の実行指示とともに失敗します。ランチャーは鮮度を確認しないため、既存の古いバンドルは再ビルドまで古いブラウザーコードを実行し得ます。プロセスは起動環境を継承し、`runProfile` はエントリーのマウント前にそのスナップショットから送信プロキシを解決するため、`HTTP_PROXY`／`HTTPS_PROXY`（および `.env` 層で宣言されたプロキシ）は追加フラグなしに適用されます。ソースエントリーはリンク済みプロファイル解決を明示的に選択するため、tsx ワークスペースインポートとプロファイルプラグインはモジュール同一性を共有します。インストール形式は、リポジトリを再ビルドせずにビルド済み `apps/cli/lib/bin.js` をランタイムプロファイル解決で起動します。
